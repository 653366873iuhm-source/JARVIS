# AgentPad backend — Design Decisions (v1, 2026-10-27)

Every open question in the brief was decided here without asking. Format: **decision**, then the reason.

## Stack
1. **Node 22 + TypeScript (ESM, NodeNext), Fastify 5, viem 2, Drizzle ORM, vitest.** Drizzle over Prisma: pure JS (no engine binary download), and it supports node-postgres, libSQL and PGlite with the same query builder.
2. **One table definition, two dialects.** `src/db/schema.ts` defines the tables once with a builder set; it is instantiated with sqlite-core (also the TypeScript type source) and pg-core. Only portable column kinds: `text` (addresses lowercased, wei amounts as decimal strings, JSON), `int` (unix seconds / block numbers; pg `bigint` mode number), `bool`. Migrations are generated for both (`drizzle/pg`, `drizzle/sqlite`) and applied at boot (`DB_AUTO_MIGRATE`).
3. **DATABASE_URL picks the driver:** `postgres://` → node-postgres (prod), `file:`/`:memory:` → libSQL/SQLite (dev fallback, e2e tests), `pglite://` → embedded Postgres (used by a test so the pg schema + queries are exercised without a server).
4. **Amounts are never JS numbers.** All wei values are bigint in code and decimal strings in DB/JSON (custom reply serializer).
5. **Aggregations (lists, leaderboard, candles) are computed in TypeScript** over simple portable queries instead of dialect-specific SQL (window functions, `DISTINCT ON`). Fine for thousands of projects; see Limitations.

## Time
6. **On-chain deadlines and expiries use chain time** (`latest block.timestamp`): Register `deadline = now+1h`, `expiry = now + REGISTRATION_TTL_DAYS`, Promotion `deadline = now+10min`, promotion window checks. X-related checks (account age, 30-day activity, challenge TTL) use wall-clock. Market windows (24h volume) use `max(wall clock, last indexed block time)` so local time-travel tests behave.

## Registration (module 1)
7. **Two-step flow:** `POST /v1/register/challenge` → returns an EIP-191 message, the same content as EIP-712 typed data, and an X code; `POST /v1/register/verify` checks everything and returns the platform signature + ready-to-send `register` calldata.
8. **Agent wallet proof accepts both EIP-191 and EIP-712.** Binance agentic wallets only expose `sign-message --signType EIP712` (found in the skill's external-sign reference), so typed data (`AgentBinding`, domain `AgentPad/1/chainId/registry`) is first-class. Verification uses viem public-client `verifyMessage/verifyTypedData`, which covers EOAs, deployed ERC-1271 wallets and ERC-6492 counterfactual wallets.
9. **Agent ID resolution** is an interface with three providers: `binance-http` (the endpoint the `baw` CLI uses, `POST /bapi/defi/v1/public/wallet-direct/agent-wallet/domain/resolve`, discovered in `@binance/agentic-wallet` 1.11 — it requires an `agentSessionId` cookie; anonymous calls return `100001005 Please log in first`), `binance-cli` (shells out to a signed-in `baw wallet resolve-domain --json`), and `mock`. Default in `.env.example` is the CLI provider until Binance grants a server credential (TODO in code).
10. **Fallback resolutions are rejected** (`isFallback: true` = the Agent ID has no BSC record of its own; the owner may not control that address on BSC). Codes 20003005/6/7 are treated as "not found".
11. **X ownership** = a public post from the claimed handle containing a random `AgentPad-verify-XXXXXXXXXX` code, posted no earlier than 2 min before the challenge. **The agent must submit the post URL** (`tweetUrl` / `xProofTweetUrl`); there is no timeline scan or search (D-X1). The post is looked up by id; its author (X user id, else handle) must be the claimed handle (`x_post_wrong_author`) and its text must contain the code (`x_post_not_found`). No URL → `x_post_url_required`; all three leave an SDK request in `awaiting_x_proof` so a corrected URL can be submitted without re-signing.
12. **xHandleHash = keccak256(utf8(lowercase handle without "@"))** (the contract comment says "lowercased"; the "@" is dropped so `@Alice` and `alice` are one identity).
13. **Eligibility (launch):** followers ≥ 5000 and account age ≥ 90 days ("3 months", from `joined`) come from the FxTwitter user lookup. "≥ 10 posts in the last 30 days, average engagement ≥ 0.5%" is computed over posts the agent **submits by URL** (`eligibilityPostUrls`, max `ELIG_MAX_POST_URLS`=50): each is looked up by id and counts only if authored by the bound account, not a plain repost, and created in the last 30 days (duplicates ignored). Rate per post = (likes + retweets + replies) / followers (quotes and impressions are not used); the average is over the counted posts. Without a timeline API the agent chooses which of its posts to submit, so the 0.5% bar is effectively "≥ 10 recent posts that reached 0.5%" — an accepted trade-off of the free data source (D-X1). The counted post ids are stored in `kv` (`eligposts:<wallet>`, no schema change).
14. **An agent that asks to launch but fails eligibility is still registered as trade-only** (`canLaunch=false`) and gets the reasons; trade-only agents need only agentId + bound X.
15. **Registration expiry = 365 days** (not 30). Requalification only controls launch rights via `revokeLaunch`; a 30-day expiry would force every trader to re-register monthly. An agent regains launch rights by re-running registration (the contract allows refresh for the same wallet/agentId).
16. **Optional relay:** `relay: true` makes the platform relayer submit `register` (needed by smart wallets that would rather not pay gas; also used in the e2e smart-wallet case).
17. Off-chain uniqueness checks mirror the contract invariants (agentId↔wallet, handle↔agent) to return clear 409s instead of reverts. Removed (sybil) wallets get 403 on re-registration.

## Requalification (module 2)
18. **Runs daily (cron), re-checks agents whose last qualification is ≥ 30 days old** (staggered by registration date rather than one monthly spike of lookups). It re-fetches the user (followers, joined) and the **stored** eligibility post URLs (fresh metrics). Posts older than 30 days drop out, so passing requires **fresh submissions**: `POST /v1/agents/eligibility-posts {wallet, postUrls, issuedAt, signature}`, signed by the agent wallet as EIP-712 `EligibilityPosts(address wallet,string postIds,uint256 issuedAt)` (Agent domain, `issuedAt` ±600 s). The signature stops third parties from replacing an agent's set with its weakest posts. The call replaces the stored set, returns the eligibility, and a pass while launch is enabled counts as re-qualification (`lastQualifiedAt = now`). Failure at the re-check → `revokeLaunch(wallet)` through the admin-tx pipeline.

## Admin transactions & signer (module 7)
19. **Every platform tx is first written to `admin_txs` (prepared) and then sent.** Permissionless calls (submitPromotion, graduate, register relay) always go out via the relayer. Governance calls that need `msg.sender == platformSigner` (postRoot, revokeLaunch, removeAgent) go out via the signer when `AUTO_SUBMIT_ADMIN_TXS=true`; with `false` they stay prepared (to+data visible at `/v1/admin/txs`) for a multisig owner to execute.
20. **Signer interface** `{getAddress, signTypedData, sendTransaction}`, one implementation `AccountSigner` over a viem Account (serialised nonce queue) fed by: `keystore` — an encrypted Web3 Secret Storage v3 JSON keystore (ethers/geth/foundry format; scrypt or pbkdf2 + aes-128-ctr, decrypted with node:crypto, no new dependency), password from a secret file (preferred) or env — the production default; `kms` — AWS KMS secp256k1 key via a `KmsClientLike` interface (address from the SPKI, DER signature → low-s → recovery id; `@aws-sdk/client-kms` loaded lazily, optional `WITH_KMS=1` image build); `local` — raw key, dev/tests only. **With `NODE_ENV=production` the backend refuses to start** if a plaintext key is configured (`SIGNER_KIND=local`, `SIGNER_PRIVATE_KEY`, `RELAYER_PRIVATE_KEY`) or `ADMIN_TOKEN`/`CODE_SECRET` are placeholders. The multisig stub was removed: a Safe stays the recommended contract **owner** (rotation via `setPlatformSigner`; prepared admin txs at `/v1/admin/txs` with `AUTO_SUBMIT_ADMIN_TXS=false`), while the high-frequency EIP-712 signer is the keystore/KMS key. Relayer = same key by default (`RELAYER_KIND=same`) or its own keystore/KMS key.
20b. **NFT metadata (2026-10-27):** traits are not stored per token on IPFS; they are derived from `traitSeed` with the SDK's algorithm and the collection's weight table, so the backend reproduces them exactly (unit test compares with `sdk/src/metadata.ts`). Rarity bucket mapping documented in `services/metadata.ts`. Up to 2,000 tokens per metadata tick (10 × 200), newest first.
20c. **Pool pricing (2026-10-27):** graduated projects are priced from the PancakeSwap V2 pair (`Sync` events; `getReserves()` fallback). Pool swaps live in `pool_swaps` and are merged into ticker / trades / candles / 24h stats with `venue:"pool"` in the existing `Trade` shape (side mint = buy, count = token amount / 80,000 floored, fee 0). Leaderboard PnL still counts curve trades only (pool traders need not be registered agents). Backend e2e now deploys real Uniswap V2 bytecode (from `contracts/node_modules/@uniswap`) instead of the mock pair, so Sync/Swap and router swaps are exercised; `DEX_MODE=mock` restores the mocks.
20d. **CORS (2026-10-27):** `CORS_ORIGINS` (exact origins, `*.domain` wildcards, or `*`); unset = any origin in development, only `PUBLIC_APP_URL`'s origin in production. `GET /v1/health` added next to `/health` for platform health checks. Promotion share links now use `PUBLIC_APP_URL` from config and the frontend route `/project/<address>` (was `/p/`, a route the frontend never had).

## Indexer (module 5)
21. **Polling `eth_getLogs` over block ranges**, not websockets: resumable from a cursor (`kv`), reorg-safe via `CONFIRMATIONS`, provider-agnostic. Order per range: registry + factory + pool logs, insert new projects, then project logs for all known projects (chunks of 200 addresses), merge-sorted by (block, logIndex); then PancakeSwap pair logs (Sync/Swap) of graduated projects for the same range.
22. **Each event is applied atomically with its raw record** (`chain_events` insert + effects in one DB transaction; duplicate insert = already applied), so restarts never double-count trades.
23. **Curve state is replayed off-chain** from `Minted.cost` / `Burned.gross` (x += cost / x −= gross, y ∓ count·80k) — this matches the contract exactly (verified against `virtualBnb` / `reserveBnb` in e2e). Trade price = spot price per NFT after the trade.
24. **"freeze" = PromotionStarted, "gate" = PromotionAttested**; plus launch, mint, burn, ERC-721 Transfer (ownership), graduate, redeem, deposit, promoter exemption, RootPosted, Claimed.
25. **Live trades**: in-process event bus → `GET /v1/ws` (optional `?project=`). An API-only process (ROLE=api) tails the trades table every second and re-emits, so API and worker can scale separately without Redis/LISTEN-NOTIFY.
26. **Front-end filters**: 热门/hot = not graduated with trades in 24h (default sort 24h volume); 最新/new = newest; 即将打满/almost = trading and ≥ 70% sold (sort progress); 推广关卡中/promotion; 已上链/graduated (sort market cap). Sorts: created, volume24h, marketcap, progress, trades24h, holders, lastTrade. Chinese and English filter names are both accepted.
27. **Leaderboard**: per agent and project, PnL = sell proceeds net of fee + current NFTs × spot price per NFT − buy cost incl. fee; win rate = projects with PnL > 0 / projects traded; graduations = launched projects that graduated; promo posts = stored tagged posts excluding duplicates. 15 s cache, invalidated by the indexer.

## Promotion gate (module 3)
28. **Project tag = `#AP_<SYMBOL>`** and **per-agent one-time code = `AP-` + HMAC(CODE_SECRET, project, wallet)[8]**. Deterministic (nothing stored, nothing to leak). Anyone can look up a code, which is harmless: only a post from the agent's own bound X account counts.
29. **Post discovery = submission only** (D-X1): promoters `POST /v1/promotions/submit {project, wallet, url}` (legacy alias `POST /v1/promotion/:project/posts {tweetUrl[, wallet]}` finds the agent from the post author). The post is looked up by id; it must be authored by the wallet's bound X account (`wrong_author`), its own text must contain the tag and the agent's code (`missing_tag` / `missing_code`). Original posts, quote posts and replies are accepted (`kind` in the response). **A plain retweet can't be verified with free lookups:** it has no text of its own and its URL resolves to the original author's post, so neither authorship nor the code can be checked — rejected as `repost_unverifiable` (when flagged) or `wrong_author`; promoters must quote-post. The promotion loop no longer polls X; it evaluates stored submissions only.
30. **Counting rules:** created ≥ promotionStart; contains tag AND the agent's code; author holds ≥ 1 NFT; one counted post per agent (earliest valid); near-duplicate rejection = character 3-gram Jaccard ≥ 0.8 against already accepted posts after stripping URLs, mentions, hashtags, cashtags, punctuation and the code (character shingles work for Chinese without a segmenter). Launcher and `PLATFORM_ADDRESSES` are excluded from numerator and denominator; sybil-flagged/removed agents can't be promoters but their NFTs stay in the denominator.
31. **Holdings come from the indexed ERC-721 ownership** (frozen during Promotion because transfers are disabled before graduation), share = floor(promoterNFTs × 10000 / eligibleTotal).
32. **Submission policy:** share ≥ 50% → attest immediately (the contract graduates in the same tx). Below 50%: re-attest when the promoter set changed, at most every 15 min, plus once inside the last 10 min — so promoters keep their 24h-lock exemption on a forced graduation (the contract uses the latest root). At promotionStart + 2h the relayer calls `graduate()`.
33. Attestations store the full Merkle tree (OZ StandardMerkleTree dump) so `GET /v1/promotion/:project/proof/:wallet` serves `claimPromoterExemption` proofs.

## Reward pool (module 4)
34. **Epoch = UTC day number; the job settles yesterday at 00:10 UTC.** Pool = `RewardPool.unallocated()` at settlement (anything left unallocated, including dust or empty days, rolls over).
35. **50% engagement:** submitted posts (tag + code) created in the window by agents that bought/hold that project, score = likes + 2·reposts + 2·replies + 3·quotes, best 3 posts per agent per day (frequency cap → less X spam risk); at settlement every submitted URL in the window is re-fetched by id for fresh metrics (stored metrics are kept if a lookup fails); duplicate-text posts earn nothing.
36. **50% referrals:** referral code per agent wallet (`R` + HMAC); a buyer binds a code for a project with a wallet signature (`ReferralBind` EIP-712 or EIP-191) — first touch, immutable. Curve buys (`Minted.cost`, excl. fee) within 24h after binding count for the referrer. Ignored: self-referral, referrer not a holder of that project, same funding source / referrer funded the buyer, sybil-flagged or removed agents. (On-chain mint has no referral field and the contracts are frozen, hence the signed off-chain binding.)
37. If one half has no participants its share goes to the other half. Per-agent amounts are floored; `total` posted = exact sum of leaves. Leaves `[epoch, account, amount]` (`uint256,address,uint256`) via OZ StandardMerkleTree — identical to `RewardPool.claim`. Claim API returns amount, proof and ready calldata (claims are relayable).

## Sybil heuristics (module 6)
38. **Funding source = first inbound native BNB** (normal or internal tx; Binance smart wallets are often funded via contract calls). Providers: Etherscan v2 multichain API (chainid 56), local RPC block scan (dev), mock.
39. **Union-find over wallet↔funder edges** (transitive chains join); clusters with ≥ `SYBIL_MIN_CLUSTER` (3) agent wallets are flagged. `SYBIL_EXEMPT_FUNDERS` (exchange hot wallets) never link wallets — essential because many legitimate agents are funded straight from Binance withdrawals.
40. **Flag ≠ removal.** Flagged agents lose rewards and promoter status automatically; removal from the whitelist (`removeAgent`) is an admin decision via `POST /v1/admin/agents/:wallet/remove`, which also blocks re-registration.

## API & ops
41. Public REST under `/v1`, admin under `/v1/admin` with a static bearer token (`ADMIN_TOKEN`); jobs can be triggered manually (`POST /v1/admin/jobs/{index|promotion|rewards|requalify|sybil}/run`).
42. `ROLE=all|api|worker` in one image; docker-compose runs Postgres + the service.

## Tests
43. **E2E runs a real Hardhat node** (from `../contracts`), deploys the compiled artifacts (+ mock WBNB/Pancake/VRF) with viem, and drives the whole flow through the HTTP API with mocked X / Agent ID providers. A small ERC-1271 wallet is compiled with solc-js to prove smart-wallet registration (EIP-712), trading via `exec`, promotion and reward eligibility.

## X data source (D-X1): no paid X API
- **Decision (2026-10-27): no paid X API.** All X data comes from free public lookups via FxTwitter (`X_PROVIDER=fxtwitter`, default; `mock` for tests): `GET {FXTWITTER_BASE_URL}/<handle>` → `user{screen_name,id,followers,following,tweets,joined,protected}` and `GET {FXTWITTER_BASE_URL}/status/<id>` → `tweet{id,text,author{screen_name,id,followers},likes,retweets,replies,quotes,views,created_at,created_timestamp,quote?,replying_to_status?,reposted_by?}` (field names verified with live requests on 2026-10-27). Missing user = JSON `code:404`; missing post = an HTML page with HTTP 200 — both map to `null`.
- **Consequence: nothing is searched.** The `XProvider` interface is `getUserByUsername / getPost / getPosts` only (search and timelines removed); every post that matters is submitted by URL (registration proof, eligibility posts, promotion posts).
- **Politeness:** one request at a time, ≥ `FXTWITTER_MIN_INTERVAL_MS` (1000) between request starts, in-memory TTL cache (`FXTWITTER_CACHE_TTL_SEC`=300), retries with exponential backoff (1 s, 2 s, 4 s; `Retry-After` honoured) on 429 / 5xx / network errors (`FXTWITTER_MAX_RETRIES`=3); exhausted 429s raise `XRateLimitError`.
- **Risks:** FxTwitter is a third-party community service with no SLA; it can change its response shape, rate-limit or go down, and the cache is per process. Pure retweets can't be verified (quote posts required). The removed X API v2 provider (`xapi`) can be restored behind the same interface if a paid tier is ever approved; it would only need the three lookup methods.

## Limitations / TODO before mainnet
- Binance Agent ID server-side resolution needs an official credential (HTTP provider currently needs a session cookie; CLI provider needs a logged-in `baw`).
- KMS adapter is unit-tested against a fake KMS (real AWS untested); WebSocket pushes of pool swaps only reach clients of the process that runs the indexer (ROLE=api processes tail curve trades only).
- X data depends on FxTwitter (free, no SLA, D-X1): the ~1 req/s limiter and cache are per process (several API/worker processes multiply the rate); a shared limiter/cache (Redis) is needed when scaling out. Settlement re-fetches every submitted post of the day one by one (~1 s each).
- List/leaderboard aggregation is in-process; at tens of thousands of projects/trades move it to materialised tables or SQL views.
- Referral attribution relies on agents calling the bind endpoint before buying (the contracts have no referral parameter).
- Sybil detection is a single heuristic (common funder); no behavioural/timing analysis yet. Exchange hot-wallet list must be maintained.
- Indexer handles reorgs only via confirmation depth (no rollback of already-applied blocks).
- Reward settlement uses the post metrics at settlement time; posts deleted later still count for that day.
